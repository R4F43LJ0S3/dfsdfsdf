# Documento de Contexto y Auditoría de Seguridad del Módulo de Login — SIFTC (ALZA)

> **Marco normativo principal:** ISO/IEC 27001:2022 (Anexo A, Control **A.8.5 Autenticación segura**) e ISO/IEC 27002:2022 (Numeral **8.5 Autenticación segura** y controles relacionados: **5.15**, **5.16**, **5.17**, **5.34**, **8.15**, **8.24**, **8.26**, **8.28**, **8.29**).  
> **Nota obligatoria sobre normas ISO:** Dado que ISO/IEC 27001:2022 e ISO/IEC 27002:2022 son estándares sujetos a derechos de autor sin copia oficial incrustada en este proyecto, **todo requisito atribuido a ISO/IEC 27001/27002 en este documento debe verificarse contra la copia oficial licenciada de la norma**.  
> **Guías técnicas abiertas complementarias (separadas explícitamente de ISO):** NIST SP 800-63B, OWASP ASVS v4.0.3 y especificación algorítmica de Blowfish/BCrypt.  
> **Estado del documento:** **Alcance Frontend + Contrato OpenAPI (`docs/api/openapi-v1.json`) — Fases 1, 2 y 3 depuradas tras limpieza de archivos obsoletos** (Propuesta en backlog pendiente de aprobación).

## 0. Alcance y Limitaciones de la Auditoría e Implementación

1. **Alcance exclusivo de Frontend (`frontend-siftc`):** Este documento audita y propone mejoras únicamente sobre el módulo de inicio de sesión y gestión de sesión del **Frontend**.
2. **Backend como servicio externo:** El servidor de la API es mantenido y desplegado de forma independiente por otro equipo en **Render (`https://siftc.onrender.com`)**. El equipo de Frontend no tiene acceso ni participación en ese despliegue.
3. **Eliminación y exclusión definitiva del backend local:** El backend local (`..\SIFTC`) y sus artefactos de aprovisionamiento en Docker fueron descartados y eliminados del análisis del equipo Frontend. No existe backend local de trabajo. La **única fuente oficial de verdad** para cualquier verificación o integración con la API es [`docs/api/openapi-v1.json`](./api/openapi-v1.json) (contrato OpenAPI 3.1.1 provisto por el servicio desplegado en Render). Los puntos de la **Sección 4.3** se formulan como preguntas de verificación y expectativas normativas para el equipo de Backend, sin afirmar la implementación interna del servidor.
4. **Fuente única de verdad del contrato de la API:** Toda verificación contra la API se rige por [`docs/api/openapi-v1.json`](./api/openapi-v1.json) (especificación OpenAPI 3.1.1 del servicio desplegado). Si cualquier documento antiguo contradice ese archivo, prevalece `docs/api/openapi-v1.json`.
5. **Restricción estricta sobre pruebas:** Todas las pruebas del Frontend son **100 % locales con datos simulados**. No se ejecutan pruebas de fuerza bruta, carga ni inyección contra `https://siftc.onrender.com`.
6. **Eliminación del modo simulado (mock):** El modo mock de datos y login simulado (`VITE_USE_MOCK`, `USE_MOCK`) de la primera entrega fue completamente eliminado de `src/services/api.js`. Todas las llamadas del Frontend se dirigen exclusivamente contra el servicio externo en Render (`https://siftc.onrender.com`), gobernado por [`docs/api/openapi-v1.json`](./api/openapi-v1.json).

## 1. Resumen del Módulo de Login

### 1.1. Arquitectura y Tecnologías (Vista desde el Frontend)
* **Frontend (SPA):** React 19 + Vite 8 + React Router v7 + Axios (`src/`).
* **Servicio Backend Externo:** API REST `SIFTC.Api | v1` desplegada en `https://siftc.onrender.com/`, cuyo contrato público está definido en [`docs/api/openapi-v1.json`](./api/openapi-v1.json) y cuyas respuestas de error siguen el formato **RFC 9457 (`application/problem+json`, esquema `ProblemDetails`)**.
* **Mecanismo de Sesión:** Autenticación basada en **JWT (JSON Web Token - RFC 7519)** enviado en la cabecera HTTP `Authorization: Bearer <token>` y control de acceso basado en roles (**RBAC**) en las rutas del cliente (`src/constants/roles.js`, `src/routes/ProtectedRoute.jsx`).

### 1.2. Flujo Paso a Paso de Autenticación en el Frontend
1. **Despertar preventivo (`src/main.jsx:10` → `src/services/api.js:100-112`):** Al cargar la SPA, `despertarBackend()` envía un `GET /health` (`docs/api/openapi-v1.json:336-352`) con reintento ante arranque en frío de Render.
2. **Captura y sanitización en cliente (`src/pages/Login.jsx:89-153` → `src/constants/validaciones.js:51-248`):** Se eliminan caracteres invisibles de control (`REGEX_CONTROL_E_INVISIBLES`) y se limita la entrada a `120` caracteres para usuario/correo y `64` para contraseña.
3. **Verificación local anti-fuerza bruta (`src/pages/Login.jsx:159-171` → `src/utils/controlIntentosLogin.js:45-60`):** Consulta en `localStorage` (`siftc_seguridad_intentos_login`) si la interfaz está bloqueada temporalmente (5 min tras 10 fallos) o en enfriamiento entre clics (`800 ms`).
4. **Normalización y petición HTTP (`src/services/api.js:165-199` → `src/utils/texto.js:4-11`):**
   * El identificador se normaliza en `NFC`, sin espacios extremos y en minúsculas (`normalizarIdentificador`).
   * La contraseña se normaliza únicamente en forma canónica `NFC` sin alterar mayúsculas ni símbolos (`normalizarPassword`).
   * Se envía `POST /api/v1/auth/login` con el cuerpo JSON `{ usuario, password }`.
5. **Recepción y adaptación de la sesión (`src/services/adaptadores.js:57-87`, `src/context/AuthContext.jsx:76-94`):**
   * El servicio externo responde `HTTP 200` con el esquema `AuthResponseDto`: `{ token, expiraEn, usuario: { id, nombre, rol } }` (en modo simulado local `src/services/api.js:142` usa una duración de 8 horas; en el servidor real `openapi-v1.json:855-862` solo declara `expiraEn` como entero `int32`, siendo las 8 horas un *valor observado en la copia local, a verificar con la respuesta real del login*).
   * El frontend adapta el objeto (`aSesion`), rescata el rol o email desde el payload del JWT si es necesario (`src/utils/jwt.js`) y guarda `token` y `usuario` en `localStorage`.
6. **Autorización y expiración en el cliente (`src/services/api.js:41-68`, `src/routes/ProtectedRoute.jsx:5-24`):**
   * Antes de cada petición HTTP y al recuperar el foco de la ventana (`AuthContext.jsx:64-74`), `esTokenVigente(token)` verifica el claim `exp` del JWT.
   * Si el token expiró o si cualquier endpoint protegido responde `HTTP 401`, el cliente limpia `localStorage` y redirige a `/login`.

### 1.3. Evidencia del Contrato OpenAPI (`docs/api/openapi-v1.json`): Qué Confirma y Qué No Confirma

* **Lo que `docs/api/openapi-v1.json` SÍ confirma:**
  1. **Únicos endpoints de identidad publicados:** Solo existen `POST /api/v1/auth/login` ([`openapi-v1.json:666-725`](./api/openapi-v1.json#L666-L725)) y `POST /api/v1/usuarios/registrar` ([`openapi-v1.json:727-825`](./api/openapi-v1.json#L727-L825)).
  2. **Inexistencia de endpoints de cierre, renovación, recuperación o MFA:** El contrato confirma que **NO existen** endpoints para `logout` (revocación de token), `refresh`, recuperación/restablecimiento de contraseña, ni segundo factor (`MFA`).
  3. **Contrato de Login (`POST /api/v1/auth/login`):**
     * Entrada (`AutenticarUsuarioCommand`, [`L829-843`](./api/openapi-v1.json#L829-L843)): `{ usuario: string, password: string }`.
     * Salida (`AuthResponseDto`, [`L844-887`](./api/openapi-v1.json#L844-L887)): `{ token: string, expiraEn: int32, usuario: { id: uuid, nombre: string, rol: string } }`.
     * Códigos HTTP documentados ([`L693-724`](./api/openapi-v1.json#L693-L724)): **únicamente `200 OK` y `401 Unauthorized` (`application/problem+json`)**. No documenta `429 Too Many Requests`.
  4. **Contrato de Registro (`POST /api/v1/usuarios/registrar`):**
     * Seguridad y descripción ([`L733, 819-823`](./api/openapi-v1.json#L733)): Exige token `Bearer` y documenta *"Requiere rol Administrador. Devuelve el identificador UUID del usuario creado"*.
     * Entrada (`CrearUsuarioCommand`, [`L888-916`](./api/openapi-v1.json#L888-L916)): `{ email, password, primerNombre, primerApellido, idRol }` (declarados como `type: string` sin restricciones de longitud o patrón en el esquema).
* **Lo que `docs/api/openapi-v1.json` NO confirma ni descarta (No verificable desde el Frontend):**
  1. Si el servidor desplegado aplica *rate limiting* interno o bloqueo de cuentas.
  2. Si el backend verifica el estado de la cuenta (`activo`/`inactivo`/`bloqueado`) antes de emitir el JWT.
  3. Si el backend registra una bitácora de auditoría de intentos exitosos y fallidos de login.
  4. Qué configuración interna de hash de contraseñas emplea el servidor en producción, si aplica *dummy hash* o qué reglas internas de complejidad ejecuta al registrar usuarios.

### 1.4. Atribución Normativa Exacta: ISO/IEC 27001 y 27002 vs. NIST, OWASP y BCrypt

| Fuente normativa / técnica | Qué aporta exactamente cada fuente |
| :--- | :--- |
| **ISO/IEC 27001:2022 (Anexo A: A.8.5, A.5.15, A.5.16, A.5.17, A.5.34, A.8.15, A.8.24, A.8.26, A.8.28, A.8.29) e ISO/IEC 27002:2022 (§8.5, §5.17)**<br>*(Verificar contra la copia oficial de la norma)* | • **§8.5:** No mostrar los caracteres de la contraseña al ingresarla; validar las credenciales solo después de haber ingresado todos los datos de entrada; no mostrar mensajes de error que revelen qué parte de los datos de autenticación es correcta o incorrecta; limitar el número de intentos fallidos de inicio de sesión (bloqueo, retardos o controles adicionales); registrar intentos exitosos y fallidos; generar eventos/alertas de seguridad ante posibles ataques; desconectar sesiones tras un periodo definido de inactividad; aplicar MFA según criticidad *(verificar contra la copia oficial de la norma)*.<br>• **§5.17:** Proteger la información secreta de autenticación en tránsito y almacenamiento; exigir contraseñas de calidad acordes a la política organizacional, impedir la reutilización reciente y verificar la identidad antes de restablecer claves *(verificar contra la copia oficial de la norma)*. |
| **NIST SP 800-63B (§5.1.1.2 Memorized Secret Verifiers)** *(Estándar abierto, no ISO)* | • Fija el umbral numérico específico de **mínimo 8 caracteres** para contraseñas nuevas y soporte de al menos **64 caracteres**.<br>• Exige **comparar las nuevas contraseñas contra listas negras de contraseñas comunes, de diccionario o filtradas en brechas previas**.<br>• Exige **permitir todos los caracteres ASCII imprimibles, espacios y caracteres Unicode** sin bloquear símbolos especiales. |
| **OWASP ASVS v4.0.3** *(Estándar abierto, no ISO)* | • **V2.1.1 / V2.1.2:** Mínimo 12 caracteres recomendados (8 como mínimo aceptable) y permitir al menos 64 caracteres **sin truncamiento silencioso** (*no password truncation*).<br>• **V2.1.4:** Permitir cualquier carácter Unicode imprimible, incluidos espacios.<br>• **V2.1.7:** Validar que la contraseña nueva no figure en listas de claves comprometidas/comunes.<br>• **V2.2.1:** Controles anti-automatización contra fuerza bruta.<br>• **V3.3.1 / V3.3.2:** Invalidación de sesión al cerrar sesión y cierre por inactividad (*idle timeout*).<br>• **V3.4.1–V3.4.3:** Atributos `Secure`, `HttpOnly` y `SameSite` en cookies.<br>• **V14.4.1–V14.4.7:** Cabeceras HTTP de seguridad (`Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`). |
| **Especificación algorítmica de Blowfish / BCrypt** *(Limitación criptográfica, no ASVS ni ISO)* | • El algoritmo Blowfish subyacente en BCrypt procesa internamente **un máximo de 72 bytes UTF-8** y descarta silenciosamente cualquier byte adicional. Validar en el cliente que la contraseña no supere los **72 bytes UTF-8** evita el truncamiento silencioso (cumpliendo OWASP ASVS V2.1.2). |

## 3. Matriz de Cumplimiento ISO/IEC 27001:2022 (Fase 2 — Recalculada sobre Controles Verificables)

> **Fórmula y metodología de cálculo:** Cada ítem técnico **verificable desde el Frontend o confirmado por `docs/api/openapi-v1.json`** recibe un puntaje: **`Cumple` = 1,0 punto**, **`Parcial` = 0,5 puntos** y **`No cumple` = 0,0 puntos**. Los controles que dependen exclusivamente de la lógica interna del servidor externo y no se exponen en el OpenAPI se marcan como **`No verificable desde el frontend`** y **se excluyen del denominador**:
> $$\text{\% Cumplimiento} = \frac{(\text{Cumple} \times 1{,}0) + (\text{Parcial} \times 0{,}5) + (\text{No cumple} \times 0{,}0)}{\text{Total de ítems verificables}} \times 100$$

## 7. Decisiones de Diseño y Pendientes

1. **Separación entre validación de contraseña en Registro vs. Login (8 caracteres NIST SP 800-63B vs. 12 OWASP ASVS V2.1.1 y límite en bytes UTF-8):**
   * **En Registro de usuarios nuevos (`PASSWORD_MIN_REGISTRO = 8`):** La longitud mínima aplica **exclusivamente al crear o cambiar contraseñas nuevas** (`registrarUsuario`). Se propone un mínimo de **8 caracteres** alineado con **NIST SP 800-63B (§5.1.1.2)** (frente a los 12 sugeridos por OWASP ASVS V2.1.1) para mantener consistencia con las políticas de contraseñas semilla de laboratorio empleadas en el proyecto.
   * **En el formulario de Login:** El formulario de inicio de sesión **NO debe aplicar longitud mínima ni mostrar reglas de formato de contraseña**, exigiendo únicamente que el campo no esté vacío y no supere el límite superior en **bytes UTF-8 (`≤ 72 bytes` / `64` caracteres)** por el truncamiento interno de Blowfish/BCrypt. Esto cumple con **ISO/IEC 27002:2022 §8.5** (*verificar contra la copia oficial de la norma*) al no revelar pistas sobre la estructura de las claves y evita bloquear a usuarios existentes cuyas contraseñas antiguas sean más cortas.
2. **Almacenamiento del JWT en `sessionStorage` + `BroadcastChannel` vs. Cookies `HttpOnly`:**
   * Dado que el servicio externo ([`docs/api/openapi-v1.json:844-866`](./api/openapi-v1.json#L844-L866)) entrega el JWT en el cuerpo JSON y no mediante cookies `HttpOnly`, migrar de `localStorage` a `sessionStorage` en el Frontend solo reduce la persistencia en disco en equipos compartidos, pero **no protege contra XSS** y es aislado por pestaña (por lo que se complementa con `BroadcastChannel` para propagar el cierre de sesión). El paso a cookies `HttpOnly; Secure; SameSite` queda como decisión arquitectónica pendiente del equipo Backend.
3. **Decisiones vigentes de estandarización del Frontend (conservadas tras retirar `VERIFICACION_ESTANDARIZACION_AUTH.md`):**
   * **Catálogo RBAC (`src/constants/roles.js`):** Se mantienen los 6 roles oficiales del dominio (`Administrador`, `Analista financiero`, `Gerente`, `Data Steward`, `Auditor`, `Usuario móvil`) comparados con normalización Unicode `NFC`.
   * **Adaptador de sesión (`aSesion` en `src/services/adaptadores.js`) y utilidad JWT (`src/utils/jwt.js`):** Se conserva el adaptador que normaliza la respuesta de `/api/v1/auth/login` a `{ token, usuario }` y el decodificador Base64URL con `TextDecoder('utf-8')` que valida la vigencia del claim `exp`.
   * **Manejo de errores RFC 9457 (`src/services/authService.js`):** Se mantiene la lectura de respuestas `application/problem+json` (`ProblemDetails`), pendiente de forzar siempre mensaje neutro cuando el código sea `401` en login (**B-07 FE**).
4. **Hosting definitivo del Frontend (B-09 FE):**
   * **Pendiente (depende de la decisión del líder del equipo):** Cuando el líder confirme el servicio de hosting definitivo, se declararán allí las cabeceras HTTP `Content-Security-Policy` (`frame-ancestors 'none'`) y `X-Frame-Options: DENY`.
5. **Controles con dependencia organizacional / documental:**
   * **MFA (A.8.5):** Requiere soporte en Backend y definición en la Declaración de Aplicabilidad (SoA).
   * **Procedimiento de restablecimiento por Administrador (A.5.17):** Requiere instructivo documental de verificación de identidad.
   * **Privacidad de datos personales (A.5.34):** Requiere enlace o texto del aviso de privacidad institucional.

## 8. Glosario Breve de Términos de Seguridad

* **BCrypt y límite de 72 bytes:** Función de hashing de contraseñas basada en el cifrado Blowfish con *salt* aleatorio y factor de costo exponencial. Por diseño interno de Blowfish, solo procesa los primeros **72 bytes UTF-8** de una contraseña, razón por la cual la longitud máxima debe validarse en bytes UTF-8 y no solo en caracteres.
* **BroadcastChannel API:** Interfaz nativa del navegador que permite comunicar mensajes entre distintas pestañas del mismo origen (por ejemplo, para propagar el cierre de sesión).
* **CSRF (*Cross-Site Request Forgery*):** Ataque que fuerza al navegador de un usuario autenticado a enviar peticiones no intencionadas cuando las credenciales (como cookies sin `SameSite`) se adjuntan automáticamente.
* **Enumeración de usuarios:** Vulnerabilidad en la que el sistema revela si un usuario existe o no mediante mensajes de error específicos o diferencias en tiempos de respuesta.
* **Idle Timeout (Cierre por inactividad):** Cierre automático de la sesión cuando transcurre un tiempo definido sin interacción del usuario en la aplicación.
* **JWT (*JSON Web Token* - RFC 7519):** Formato estándar de token firmado digitalmente que contiene *claims* codificados en Base64URL (`sub`, `email`, `name`, `role`, `jti`, `exp`).
* **NFC (*Normalization Form Canonical Composition*):** Forma canónica Unicode que garantiza que caracteres acentuados o la letra `ñ` tengan siempre la misma secuencia de bytes antes de ser procesados.
* **RBAC (*Role-Based Access Control*):** Control de acceso basado en el rol asignado al usuario autenticado (`Administrador`, `Analista financiero`, `Gerente`, `Data Steward`, `Auditor`, `Usuario móvil`).
* **RFC 9457 (*Problem Details for HTTP APIs*):** Estándar utilizado por la API para devolver errores HTTP estructurados (`type`, `title`, `status`, `detail`, `instance`).
* **Shoulder Surfing:** Riesgo de que un tercero observe físicamente la pantalla o el teclado mientras el usuario escribe su contraseña.
* **XSS (*Cross-Site Scripting*):** Inyección de código JavaScript malicioso en el navegador capaz de leer cualquier dato almacenado en `localStorage` o `sessionStorage`.
